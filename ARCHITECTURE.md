# Архитектура

## Пайплайн

```
┌────────┐   ┌───────────────┐   ┌───────────┐   ┌────────┐   ┌───────┐   ┌────────┐
│ parser │ → │ design_system │ → │ generator │ → │ layout │ → │ audit │ → │ export │
└────────┘   └───────────────┘   └───────────┘   └────────┘   └───────┘   └────────┘
 PPTX → IR    IR → токены и       бриф → план     контент →     колода →    IR → .pptx
              паттерны макетов    → контент       IR слайдов    находки     .html  .pdf
                                  слайдов         (×3 варианта) (+ исправления)
```

Слева направо каждый этап принимает результат предыдущего и отдаёт вход следующему. Связывает их только `apps/server` — ни один пакет пайплайна не знает о соседе больше, чем тип данных на границе. Общий тип на границах — IR (`packages/ir_schema`): дерево слайдов с фигурами, текстом, таблицами, картинками, графиками и диаграммами.

### Что зависит от чего

| Пакет | Зависит от | Роль |
| --- | --- | --- |
| `ir_schema` | — | общий контракт: `Deck`, `Slide`, фигуры (текст, автофигура, картинка, таблица, график, диаграмма, «сквозная» фигура) |
| `parser` | ir_schema | `.pptx` → IR |
| `design_system` | ir_schema | IR → палитра, типографическая шкала, макеты со слотами |
| `inference` | — | клиент моделей, цепочка запасных, загрузка и версии скиллов |
| `generator` | design_system, inference | бриф → план → контент слайдов |
| `layout` | generator, design_system | контент → собранный слайд, три варианта |
| `audit` | generator, design_system | проверки, исправления, каталог проверок |
| `export` | ir_schema | IR → `.pptx`, векторный `.pdf`, проверка структуры файла |
| `ingest`, `brand`, `images` | inference, parser, generator | материалы задачи → фактлист; бренд-пакеты; фото по теме слайда |
| `apps/server` | все | HTTP API: оркестрация, ничего своего |
| `apps/web` | только API сервера | интерфейс |

Стрелок «назад» нет: `export` не знает про `audit`, `design_system` — про генерацию, `parser` — про шаблоны, которые встречал. Единственное место, где что-то знает про конкретный шаблон, — данные (`evals/templates`), а не код.

## Слои

### `parser`
Вход: `.pptx`. Выход: IR — каждая фигура с точными координатами, стилями и z-порядком, текст по runs, таблицы, картинки, фон слайда, тема, ссылка на макет. Что разобрать не удалось (графики, SmartArt, группы), остаётся `PassthroughShape` с исходным XML — ничего не теряется и ничего не выдумывается. Фундамент: вся точность дальше зависит от него.

### `design_system`
Вход: IR. Выход: дизайн-токены — палитра, типографическая шкала, повторяющиеся паттерны макетов (по `layout_name` автора шаблона, а не по нашим догадкам о названиях) и их слоты: заголовок, карточки, текстовая область, таблица, картинка, график, вместимость каждого блока в символах. Всё выводится из самого файла; именно здесь соблюдается требование «не хардкодить под выданные шаблоны».

### `generator`
Вход: бриф, число слайдов, длина выступления. Выход: план (`Outline`: роль-макет, вывод, секунды на слайд) → контент каждого слайда (заголовок-вывод, пункты, таблица, график или диаграмма, запрос картинки, текст выступления).
- Промпты и параметры моделей — в `skills/` отдельными файлами с версиями; в коде промптов нет.
- Текст пишется под вместимость именно того слайда шаблона, куда ляжет; срабатывание жёстких правил (выдуманная цифра, длина сверх блока, язык) чинится по лестнице: повторный проход → точечная перезапись (`text-fix`) → вырезание.
- График строится только по числам из брифа, диаграмма — по структуре; заметки спикера обрезаются до бюджета слайда по времени.
- Ни одна модель не видит слайд целиком — она пишет под слоты, а не рисует.

### `layout`
Вход: контент + токены + паттерны. Выход: три IR-колоды одним проходом. Слайд шаблона копируется целиком, меняется только содержимое слотов; график или диаграмма писателя занимают место фото-рамки или текстовой области. Ось вариантов — плотность текста плюс выбор равноценных дизайнов шаблона для каждого слайда (список из четырёх пунктов может лечь на карточки в одном варианте и на текст в другом): три варианта получаются из одного кода с параметром, а не из трёх веток. Каждый вариант остаётся в правилах шаблона: только его макеты, шрифты, шкала размеров.

### `audit`
Вход: IR колоды (+ картинки слайдов для модельных проверок). Выход: находки с типом `deterministic` или `model`.
- **Детерминированные** (26, `run_checks` + проверка файла) — по данным IR, без модели, выполняются всегда и укладываются в доли секунды.
- **Недетерминированные** (10, `run_model_checks`) — VLM по картинке слайда, по кнопке, вне 5-минутного бюджета.
- **Исправления** (`apply_fixes`) — правки IR по выбранным пользователем находкам; работают на копии, повторно прогоняют проверки.
- **Каталог** (`CATALOG`) — один список проверок для интерфейса, документации и тестов.

Полное описание — `AUDIT.md`. Находки — информация для человека, а не блокировка экспорта.

### `export`
Вход: IR. Выход:
- **`.pptx`** — слайды клонируются из самого файла шаблона (фон, мастера, тема переживают экспорт), меняется только содержимое; всё нативное и редактируемое: текст, таблицы, встроенные графики (данные правятся в PowerPoint), диаграммы и пиктограммы — группы обычных фигур, речь спикера — в заметках. Растровых слайдов нет ни в одном режиме.
- **`.html`** — один файл: те же слайды из браузерного рендера с вшитыми шрифтами и картинками, текст остаётся текстом, заметки под слайдами.
- **`.pdf`** — векторный, из `.pptx` через LibreOffice, если он есть; без него браузер рисует PDF сам.
- **`validate`** — структурная проверка файла (битые связи, типы содержимого, повторные id): то, из-за чего PowerPoint предлагает «восстановить».

## Данные и границы

- `apps/server` оркестрирует, сам логики парсинга, генерации, вёрстки, аудита и экспорта не содержит.
- `apps/web` обращается только к API. Каждое действие интерфейса — эндпоинт, так что CLI или интеграция — тот же API, а не переписывание.
- `skills/` читается `generator`, `audit`, `brand`, `ingest` во время выполнения. Изменить поведение агента — значит править файл в `skills/` и поднять `version`; `skills/skills.lock.json` и тест не дадут забыть.
- `packages/ir_schema` — единственный общий контракт. Если двум пакетам нужно договориться о форме данных, она идёт туда.

## Бюджеты и отказоустойчивость

- **5 минут на колоду.** Этапы с моделью получают дедлайны (дайджест ≤ 75 с, план ≤ 75 с, контент — весь остаток, не меньше 120 с); необязательные проходы починки запускаются, только пока успевают. Вёрстка и детерминированный аудит — секунды. Стадии стримятся в интерфейс.
- **Отказ модели не роняет генерацию.** Каждый скилл идёт по цепочке запасных моделей (402/404/429/5xx/таймаут), все — открытые веса ≤ 35B под Apache-2.0 (см. `MODELS.md`). Придуманная моделью роль макета сводится к ближайшей настоящей, неподходящая картинка — к плоскому цвету, недостающий рендер слайдов — к браузерному.
- **10–15 слайдов**: число выводится из длины выступления и зажато в этих границах; явно выбранное пользователем число слайдов уважается.

## Что проверяет «шаблон, которого не видели»

- `evals/test_unseen_template.py` собирает два шаблона с нуля (4:3 и 16:9, другие гарнитуры и палитры, макеты с названиями на кириллице и иероглифах, один вовсе без плейсхолдеров) и гонит через парсинг → дизайн-систему → вёрстку трёх вариантов → аудит → экспорт → проверку файла.
- Выбор шаблона «по теме брифа» считается по словам самого шаблона (имя файла и текст слайдов) против слов брифа; знания о конкретных шаблонах в коде нет.
