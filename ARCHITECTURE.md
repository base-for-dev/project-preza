# Архитектура

## Пайплайн

```
┌──────────┐   ┌───────────────┐   ┌───────────┐   ┌──────────┐   ┌───────┐   ┌────────┐
│  parser  │→→│ design_system │→→│ generator │→→│  layout  │→→│ audit │→→│ export │
└──────────┘   └───────────────┘   └───────────┘   └──────────┘   └───────┘   └────────┘
 PPTX → IR      IR → токены +       бриф → outline    контент +      колода →   IR →
                 паттерны макетов    → контент слайда   токены →       findings   pptx/html/pdf
                                                          собранный IR
```

Каждый этап — модуль `packages/*` с однонаправленным потоком данных: он принимает тип-выход предыдущего этапа и производит тип-вход следующего. Ни один этап не лезет во внутренности другого — `apps/server` единственное место, где они связываются вместе.

## Слои

### `parser`

Вход: файл `.pptx`. Выход: промежуточное представление (IR) — см. `packages/ir_schema`. Извлекает каждую фигуру, текстовый run, таблицу, диаграмму, изображение и ссылку на мастер/макет с точными координатами, стилями и z-порядком. Это фундамент: вся дальнейшая точность зависит от него, и здесь нет ничего заточенного под конкретный шаблон.

### `design_system`

Вход: IR. Выход: дизайн-токены — цветовая палитра, типографическая шкала, сетка/отступы, повторяющиеся паттерны макетов по роли слайда (титул, раздел, контент, сравнение, данные/график, картинка+подпись, ...). Классификация паттернов обязана обобщаться на макеты, которые раньше не встречались — именно в этом пакете либо соблюдается, либо нарушается требование «не хардкодить под 3 выданных шаблона».

### `generator`

Вход: бриф (текст) + целевое число слайдов. Выход: outline (упорядоченный список намерений слайдов) → контент по каждому слайду (текст, данные, брифы для изображений). Оркестровка через LLM; промпты живут в `skills/outline-generation` и `skills/slide-content`, не в коде. Текст пишется под реальную вместимость блока (строки × символы из геометрии слайда шаблона); нарушения жёстких правил (число, которого нет в брифе; строка длиннее блока) чинятся детерминированно: повторный проход → точечная перезапись (`skills/text-fix`) → удаление. Перед экспортом вёрстка сжимает шрифт текста, не влезающего в блок, по шкале размеров самого шаблона (в .pptx нет автоподгонки).

### `layout`

Вход: контент слайда + дизайн-токены + паттерны макетов. Выход: собранный IR слайда — контент, уложенный на паттерн, с разрешённым переполнением/подгонкой. Именно здесь живёт требование «3 варианта вёрстки»: ось вариативности — параметр на этом этапе, а не три отдельных codepath'а.

### `audit`

Вход: собранный IR колоды (+ рендер слайдов для модельных проверок). Выход: findings, помечены `deterministic` или `model`. Два независимых входа, не один вызов:

- **Детерминированные** (`run_checks`) — границы, наложения, принадлежность палитре, лимиты плотности, язык колоды (см. `AUDIT.md`) — работают напрямую по данным IR, без обращения к модели. Вызываются внутри пайплайна генерации на каждый запрос, укладываются в 5-минутный бюджет.
- **Модельные** (`run_model_checks`) — по одному вызову VLM на слайд, десять да/нет-проверок из `AUDIT.md`. Требуют рендер каждого слайда картинкой (`export.render`, нужен LibreOffice — при его отсутствии эндпоинт отвечает 501, а не падает) и стоят денег на каждый вызов, поэтому не часть основного пайплайна и не 5-минутного бюджета: отдельный, запускаемый пользователем по требованию шаг (`POST /api/audit/deep`) поверх уже готовой колоды.

Findings — информация для человека, не блокировка: ни один слайд с находками сейчас не мешает экспорту.

### `export`

Вход: проаудированный IR колоды. Выход: `.pptx` (нативные объекты — текст, фигуры, таблицы, диаграммы остаются редактируемыми), `.html`, `.pdf`. Ни одному этапу пайплайна не разрешено сплющивать слайд в растровую картинку как основной результат.

## Границы

- `apps/server` оркестрирует; сам по себе не содержит логики парсинга/генерации/вёрстки/аудита/экспорта.
- `apps/web` никогда не обращается к пакетам пайплайна напрямую — только через API `apps/server`.
- `skills/` читается `generator` и `audit` во время выполнения; изменение поведения агента никогда не должно требовать изменения кода.
- `packages/ir_schema` — единственный общий контракт между пакетами; если двум пакетам нужно договориться о форме данных, она идёт сюда, а не в самодельную передачу словарей.
