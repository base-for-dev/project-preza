# Design Philosophy

Ориентир: open-source проекты из SF/Кремниевой долины уровня Anthropic, OpenAI, Vercel, shadcn/ui, [openwork](https://github.com/different-ai/openwork). Не корпоративный энтерпрайз, не хакатонная поделка — продукт, который выглядит так, будто его уже используют тысячи разработчиков.

Название проекта TBD — впишется позже, весь остальной документ от названия не зависит.

## Дух продукта

- **Инструмент, не демо.** Каждая фича должна работать так, будто её можно продать завтра, а не "показать на защите". Хакатонный дедлайн — ограничение по времени, не оправдание для sloppy кода.
- **Прозрачная архитектура как фича.** У лучших OSS-агентных проектов (Anthropic, OpenWork) видно слои: parsing → design system → generation → layout → audit → export. Каждый слой — отдельный модуль с понятной границей ответственности, не одна большая "магическая" функция.
- **Config over code.** Промпты, чек-листы аудита, правила дизайн-токенов — отдельные версионируемые файлы (`.md`, `.yaml`, `.json`), не зашиты в Python/TS. Это и требование ТЗ, и правильная практика: агентное поведение должно быть diff-able и review-able отдельно от логики.
- **Voice: builder-to-builder.** Прямой, конкретный, без воды. Никаких "delve", "leverage", "seamless", "comprehensive solution", "cutting-edge". Пиши как инженер объясняет инженеру: что это, зачем, как запустить.

## Репозиторий

Структура — по образцу openwork/vercel-style монорепо:

```
/apps            — рабочие приложения (frontend, api/server)
/packages        — переиспользуемые модули (parser, design-system-extractor, layout-engine, audit, export)
/skills          — промпты и конфиги агентов/скиллов, версионируемые отдельно от кода
/evals           — тесты пайплайна на реальных шаблонах (не unit-тесты ради галочки)
/docs            — README, ARCHITECTURE, MODELS, AUDIT (требование ТЗ, см. project_task в памяти)
```

- Корневой `README.md` — короткий: что это, установка в 3 команды, одна GIF/скриншот, ссылка на docs. Не история проекта, не маркетинг.
- `ARCHITECTURE.md` — диаграмма пайплайна + границы слоёв, без прозы.
- Таблицы вместо абзацев везде, где можно перечислить.
- Лицензия: MIT (открытое решение — прямое требование ТЗ п.6, п.11).

## Визуальный язык (frontend / demo UI)

- Тёмная тема по умолчанию, нейтральная палитра (как у Anthropic Console, Vercel, Linear) — не "AI-слоп" из фиолетовых градиентов и блёсток.
- Типографика: один системный/моноширинный шрифт для UI, без декоративных шрифтов.
- Минимум chrome — интерфейс не должен спорить с генерируемыми презентациями, которые и есть главный визуальный артефакт.
- Пустые состояния, ошибки, прогресс генерации — обычный, человеческий текст, не "Oops! Something amazing is loading ✨".

## Что запрещено (anti-patterns)

- Эмодзи в коде, коммитах, README (см. общие инструкции пользователя — эмодзи только по явному запросу).
- Маркетинговый тон в документации ("революционное решение", "мощная платформа").
- Хардкод под 3 выданных шаблона — главный красный флаг ТЗ, прямой провал критерия generalization.
- Один гигантский LLM-промпт вместо измеримого пайплайна с валидацией на каждом шаге.
- PR/коммиты без внятного "почему" — только "что" видно из диффа, "почему" пишется в сообщении.

## Связь с остальным контекстом

Продуктовые и ТЗ-ограничения — в памяти проекта (`project_task`, `project_team`, `project_task_dates`). Этот файл — про то, **как** это должно выглядеть и ощущаться, не про то, что обязательно сделать.
